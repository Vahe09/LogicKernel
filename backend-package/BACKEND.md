# LogicKernel

Это главный документ проекта, здесь описано текущее устройство фронтенда и технический порядок подключения бэкенда в релизе

Пояснения написаны через запятые, точки и дефисы внутри имён файлов, адресов, заголовков HTTP и примеров кода сохранены, это часть технического синтаксиса

## Что работает сейчас

В проекте есть 11 курсов, в каждом по 60 уроков и 20 модулей, всего 660 уроков с практикой, объём программы каждого курса увеличен в 5 раз по количеству занятий, дополнительно есть 6 отдельных задач на JavaScript

Материалы курсов сейчас приходят из локальных файлов фронтенда, читать уроки, менять код и сохранять черновики можно без бэкенда

Выполнение пользовательского кода в браузере полностью удалено, редакторы сохраняют текст, при нажатии на отправку сейчас появляется сообщение «Проект ещё в разработке», то же самое происходит при отправке сочетанием Ctrl и Enter

В текущем режиме нет запуска кода, локальных тестов, имитации очереди, создания демопопыток и начисления награды за отправку, настоящие результаты появятся только после подключения серверной проверки

Начальная статистика, профиль и сертификаты остаются демонстрационными, старые данные браузера автоматически не удаляются, прежние локальные достижения не являются подтверждением серверной проверки

## Как открыть проект

Для просмотра достаточно открыть `index.html`, для работы через локальный HTTP запусти `start.cmd` и открой `http://localhost:4173`, для сервера нужен установленный Node, проверка проекта выполняется на Node 24

У проекта нет npm зависимостей и обязательной сборки интерфейса, остановка локального сервера выполняется через Ctrl и C в его окне

## Как устроена расширенная программа

Курсы охватывают Python, JavaScript, TypeScript, C#, Go, Rust, C, C++, HTML и CSS, SQL, алгоритмы на JavaScript

В каждом курсе уроки с 1 по 12 дают первые шаги с нуля, с 13 по 24 закрепляют основы, с 25 по 36 переходят к прикладной разработке, с 37 по 48 разбирают продвинутые задачи, с 49 по 60 посвящены инженерным решениям, которые встречаются в работе senior разработчика

После первых четырёх модулей идут 16 тематических мастерских, каждая включает реализацию, отдельное занятие по проверке и отладке, проектную работу с обоснованием решений, последнее занятие посвящено итоговому проекту курса

В новых уроках есть объяснения, предметные примеры, разбор рисков, цели, задания, критерии приёмки и файлы для реализации и отчёта, ученик должен показать граничные случаи, сравнение альтернатив и результаты проверки, одного короткого вывода программы недостаточно

Оценка времени в карточке включает самостоятельную практику и является ориентиром, сложные проекты могут потребовать больше времени, прохождение программы не гарантирует должность senior, для неё нужен опыт разработки, сопровождения и работы в команде

Идентификаторы первых 12 уроков сохранены, новые уроки продолжают последовательность до `python-60`, `js-60` и аналогично для остальных курсов, полный текст и все задания каждого курса находятся в `backend-package/courses`, JSON подходит для импорта, Markdown для чтения

## Как устроен интерфейс

Это приложение на обычных HTML, CSS и JavaScript, фреймворка и клиентского сборщика здесь нет, экран меняется по части адреса после символа решётки

Адрес `#/courses` открывает каталог, `#/course/python` открывает программу Python, `#/lesson/python/python-01` открывает конкретный урок, `#/tasks` открывает список отдельных задач, `#/task/reverse` открывает задачу на разворот строки

Браузер не отправляет часть адреса после решётки серверу, поэтому маршруты страниц не нужно повторять на бэкенде, для загрузки материалов используются отдельные HTTP запросы

Скрипты страницы подключены с `defer` и выполняются по порядку, общие объекты доступны через `window`, функции представлений обращаются к состоянию приложения после загрузки всех скриптов

## Файлы в корне

**`index.html`**, оболочка приложения, заголовок, боковое меню, область основного экрана, контейнеры уведомлений и модальных окон, здесь подключаются стили и скрипты, встроенный маленький скрипт применяет сохранённую тему до отрисовки страницы

**`styles.css`**, все стили, светлая и тёмная темы, адаптивная раскладка, карточки курсов, уроки, редакторы и окна, шрифт Manrope загружается с Google Fonts, без сети используется запасной шрифт

**`config.js`**, единственное место выбора источника данных, сейчас `mode` равен `mock`, после подключения бэкенда он должен стать `http`, поле `baseUrl` задаёт базовый адрес API, остальные поля задают задержку локальных материалов, таймаут запроса и интервалы ожидания результата

**`api.js`**, общий транспорт для материалов и решений, в режиме `mock` загружает локальные ответы курсов, отправку решений отклоняет с кодом `PROJECT_IN_DEVELOPMENT`, историю возвращает пустой, в режиме `http` отправляет JSON через `fetch`, добавляет нужные заголовки, обрабатывает ошибки, таймаут и отмену запроса, этот файл никогда не запускает полученный от пользователя код

**`app.js`**, состояние приложения, маршрутизация, главная, каталог, список отдельных задач, библиотека, достижения, профиль и настройки, здесь находятся общие функции создания разметки, иконок, уведомлений и работы с localStorage, при смене страницы старые запросы редакторов отменяются, функция `bootstrapCourses` получает каталог через `LKApi.listCourses`, функция `render` выбирает экран по адресу

**`lesson-view.js`**, программа курса и полный урок, отображение блоков теории, файлов редактора, ввода, подсказок и истории серверных попыток, сохранение черновиков, отправка практики урока и опрос её статуса в режиме `http`, в режиме `mock` кнопка отправки только показывает сообщение о разработке

**`task-submit.js`**, отправка кода из раздела отдельных задач, в режиме `mock` показывает сообщение о разработке, в режиме `http` создаёт запрос к серверу и при необходимости опрашивает состояние попытки, сохраняет ключ повторной отправки, прекращает ожидание при уходе со страницы, текст результата берёт из ответа сервера, код задачи не выполняет

**`server.mjs`**, простой сервер файлов для разработки на порту 4173, переменная окружения `PORT` позволяет изменить порт, он раздаёт файлы из папки проекта и не содержит API обучения, авторизации или выполнения кода, для публичного релиза его использовать не нужно

**`start.cmd`**, запуск локального сервера на Windows, если Node не найден, открывает HTML напрямую, папку проекта выбирает относительно своего расположения

**`README.md`**, этот полный документ, **`BACKEND.md`**, короткий указатель на документацию внутри передаваемого пакета, **`LogicKernel-backend-package.zip`**, архив материалов и контракта для разработчика бэкенда

**`verify.mjs`**, автоматическая проверка интерфейса через Microsoft Edge, запускает отдельный профиль браузера и тестовый HTTP сервер, проверяет материалы, черновики, отсутствие выполнения введённого кода и передачу решений на тестовый API, тестовый сервер возвращает заранее подготовленные ответы и не исполняет решения

**`.gitignore`**, исключает временный профиль браузерных проверок и папку зависимостей из Git, собственного Git репозитория для запуска приложения не требуется

## Папка backend-package

**`catalog-import.json`**, все 11 курсов и 660 уроков для импорта одним документом, поля верхнего уровня `schemaVersion`, `contentVersion`, `courses`, `lessons`, поле `courses` содержит полные программы с модулями

**`courses/<courseId>.json`**, один курс целиком, поля `schemaVersion`, `contentVersion`, `course`, `lessons`, этим вариантом удобно импортировать курсы независимо друг от друга

**`courses/<courseId>.md`**, читаемый текст того же курса, теория, примеры, практики и подсказки, этот формат предназначен для человека, фронтенд получает структурированный JSON

**`responses/courses/index.json`**, готовое тело ответа каталога, **`responses/courses/<courseId>.json`**, готовая программа курса, **`responses/lessons/<lessonId>.json`**, готовый полный урок, для первого подключения сервер может отдавать эти файлы без преобразования

**`task-import.json`**, публичный реестр отдельных задач для бэкенда, нужно сохранить их идентификаторы, версии, имена функций и профили исполнения, серверные тесты разрабатываются отдельно и не возвращаются фронтенду

**`manifest.json`**, версия комплекта, количества курсов и уроков, список цельных файлов курсов, соответствие 672 маршрутов материалов файлам ответов и их контрольные суммы SHA256

**`schemas/content.schema.json`**, формат оболочки ответа и всех объектов материалов, **`schemas/submission-request.schema.json`**, формат отправки практики урока, **`schemas/submission-response.schema.json`**, формат попытки и результата урока

**`schemas/task-submission-request.schema.json`**, формат отправки отдельной задачи, **`schemas/task-submission-response.schema.json`**, формат её результата, схемы используют JSON Schema и проверяются вместе с примерами

**`examples/submission-request.json`**, запрос решения урока, **`examples/submission-queued.json`**, ответ о постановке в очередь, **`examples/submission-accepted.json`**, принятое решение, **`examples/submission-wrong-answer.json`**, неверный ответ, **`examples/submission-compilation-error.json`**, ошибка компиляции, **`examples/error.json`**, обычная ошибка API

**`examples/task-submission-request.json`**, запрос отдельной задачи, **`examples/task-submission-accepted.json`**, пример подтверждённого сервером результата отдельной задачи, все файлы examples являются образцами контракта, их нельзя использовать как универсальный успешный ответ боевого сервера

**`examples/submission-review-request.json`**, полный запрос итоговой работы Python с основным файлом, компонентом и `design.md`, внутри сохранены начальные шаблоны, это пример формата отправки, для зачёта ученик должен заполнить их по условию

**`runtime-profiles.json`**, требования к начальным и инженерным средам проверки, **`fixtures/school-sqlite-v1.sql`**, начальные таблицы и записи учебной базы SQLite, **`fixtures/school-postgresql-v1.sql`**, исходная база для мастерских PostgreSQL, **`openapi.json`**, машинное описание HTTP методов

**`serve.mjs`**, запускаемый пример API материалов на порту 4180, загружает ответы из manifest, возвращает пустую историю, на отправку кода отвечает ошибкой об отсутствии проверки, пользовательский код не исполняет

**`validate.mjs`**, проверяет схемы, ссылки между курсами и уроками, порядок, версии, профили сред, контрольные суммы и совпадение экспорта с локальными материалами, **`validation-report.json`**, результат последней успешной проверки

**`README.md`** внутри пакета объясняет его содержимое, **`BACKEND.md`** содержит копию этой технической инструкции, пути приложения в ней указаны относительно корня полного проекта

## Как разместить фронтенд в релизе

На публичном сервере нужно раздавать `index.html`, `styles.css`, `config.js`, `api.js`, `app.js`, `lesson-view.js`, `task-submit.js`, `content/tasks.js` и `assets/favicon.svg`

Для режима `http` локальный комплект курсов не нужен, папки `tools`, `verification`, серверные исходники, архив и импортный пакет не нужно публиковать как часть сайта, сервер получает материалы при импорте отдельно

Предпочтительная схема размещения, статика и API находятся на одном домене через HTTPS, запросы к `/api/v1` проксируются на приложение бэкенда, остальные запросы обслуживают статические файлы

В `config.js` после готовности API должно быть такое значение, файл нужно обновить на сервере и перезагрузить страницу

```js
window.LK_CONFIG = Object.freeze({
  mode: 'http',
  baseUrl: '/api/v1',
  mockLatencyMs: 100,
  requestTimeoutMs: 10000,
  pollIntervalMs: 800,
  maxPollDurationMs: 30000
});
```

У `baseUrl` не должно быть завершающего слеша, адаптер добавляет путь метода сам, значение `mockLatencyMs` в режиме HTTP не используется

Одна смена режима подключает материалы, отправку решений и историю практик уроков, она не реализует сервер пользователей, вход, синхронизацию профиля и выдачу настоящих сертификатов

## Как бэкенду хранить курсы

Язык и фреймворк бэкенда можно выбрать любые, фронтенду важен контракт JSON, импортируй `catalog-import.json` или отдельные цельные курсы

Можно хранить программы и уроки как JSON документы, можно разделить их на таблицы курсов, модулей, уроков и упражнений, при выдаче нужно собрать исходную структуру без переименования полей

Идентификаторы курсов сейчас `python`, `js`, `algorithms`, `html`, `sql`, `ts`, `csharp`, `c`, `cpp`, `go`, `rust`, идентификатор курса `js` отличается от языка `javascript`, идентификатор `ts` отличается от языка `typescript`

Идентификаторы уроков стабильные, например `python-01`, идентификатор практики этого урока `python-01-practice`, при обновлении не нужно выдавать старому идентификатору другое содержательное назначение

## Методы получения материалов

При старте приложение вызывает следующий метод, он должен вернуть весь доступный каталог сразу, пагинация каталога на фронтенде сейчас не реализована

```http
GET /api/v1/courses
Accept: application/json
```

Успешный ответ имеет HTTP статус 200 и заголовок `Content-Type: application/json; charset=utf-8`, тело совпадает с `responses/courses/index.json`, поле `data` является массивом карточек, `meta.total` содержит количество, `meta.nextCursor` равно `null`

Для программы курса и самого урока используются следующие методы

```http
GET /api/v1/courses/python
GET /api/v1/lessons/python-01
```

Оболочка у этих ответов одна, в примере вместо содержимого показан пустой объект, реальные заполненные ответы лежат в `responses`

```json
{
  "data": {},
  "meta": {
    "schemaVersion": "1.0",
    "contentVersion": "2026.09.15.1"
  }
}
```

Карточка курса содержит `id`, `slug`, `title`, `subtitle`, `description`, `level`, `category`, `language`, `base`, `hours`, `lessons`, `teacher`, `version`, `prerequisites`, `outcomes`, поле `lessons` здесь является числом, `base` оставь равным нулю, оно не является прогрессом пользователя

Полная программа содержит те же поля и массив `modules`, каждый модуль содержит `id`, `title`, `position`, `lessons`, здесь `lessons` уже является массивом ссылок на уроки

Ссылка на урок содержит `id`, `title`, `position`, `estimatedMinutes`, `hasPractice`, позиции начинаются с нуля, позиция урока считается по всему курсу, массивы нужно отдавать уже отсортированными

Полный урок содержит `id`, `courseId`, `moduleId`, `position`, `slug`, `title`, `version`, `estimatedMinutes`, `level`, `objectives`, `blocks`, `exercise`, `references`, `navigation`, `completionPolicy`

У `navigation` есть `previousId` и `nextId`, на границе курса вместо отсутствующего урока передаётся `null`, `references` содержит ссылки с полями `label` и `url`

## Как передавать теорию

Поле `blocks` является массивом структурированных блоков в порядке чтения, сервер не должен превращать его в HTML строку, фронтенд создаёт разметку сам и экранирует текст

У всех блоков есть `id` и `type`, у типов `paragraph` и `heading` есть `text`, у `reference` есть `title` и `text`, у `code` есть `title`, `language`, `filename`, `code`

У `callout` есть `tone`, `title`, `text`, значение `tone` может быть `info` или `warning`, у `steps` и `checklist` есть `title` и массив строк `items`, у `glossary` есть `title` и массив объектов с полями `term` и `definition`

Вставлять код ученика или произвольный серверный текст через неэкранированный HTML нельзя, пример кода внутри учебного блока и код из редактора должны оставаться текстом

## Как передавать практику урока

Поле `exercise` содержит `id`, `version`, `title`, `prompt`, `language`, `runtimeProfileId`, `files`, `entryFile`, `stdin`, `publicExamples`, `hints`, `constraints`, `grading`

Каждый элемент `files` содержит `path`, `language`, `editable`, `starterCode`, сейчас все файлы редактируемые и имеют `editable:true`, блокировка редактирования для `editable:false` не реализована, служебные файлы проверки сюда не включаются

Поле `entryFile` совпадает с путём одного из файлов, `stdin` содержит `enabled`, `defaultValue`, `label`, `help`, публичный пример содержит `id`, `input`, `expectedOutput`, `description`

Поле `constraints` задаёт размеры и предлагаемые пределы исполнения, суммарный размер кода ограничен 65536 байтами UTF8, ввод ограничен 8192 байтами, сервер повторно проверяет эти пределы независимо от браузера

В текущих материалах время указано как 2000 миллисекунд, память как 128 мегабайт, это исходные настройки, их нужно откалибровать по каждой среде отдельно, особенно для компиляции и управляемых сред

В `grading.strategy` используются `program`, `query`, `document`, `review`, поле `serverOnly` равно `true`, `hiddenTestsIncluded` равно `false`, публичный пример не заменяет серверный набор проверок

У SQL дополнительно есть `fixture` с публичными учебными таблицами, на сервере каждая попытка получает новую копию учебной базы из SQL файла пакета

## Как бэкенду проверять расширенные работы

Уроки с 13 по 60 используют `grading.strategy:review`, сервер берёт правила из сохранённой версии упражнения, поле `exercise.review.kind` различает `implementation`, `verification`, `project`, массив `criteria` содержит критерии приёмки, строка `projectScope` задаёт объём работы, строка `tradeoff` задаёт вопрос о выборе решения

В этих уроках редактор содержит три файла, основной файл кода, файл компонента и документ, для реализации это `README.md`, для проверки `tests.md`, для проектной работы `design.md`, все три передаются в одном массиве `files` того же запроса `POST /api/v1/submissions`, отдельный метод загрузки отчёта не нужен

Путь документа остаётся в `files[].path`, текст в `files[].code`, поле с именем `code` используется и для Markdown, сервер сохраняет весь снимок попытки, документ не нужно компилировать или передавать интерпретатору как программу

В ответе материалов шаблон документа имеет `language:markdown`, это язык отдельного файла, язык упражнения и `runtimeProfileId` остаются языком и средой курса, сервер должен проверять разрешённые пути по версии задания и отвергать пути вне рабочей папки

Для расширенных работ используются профили `python-engineering-v1`, `javascript-engineering-v1`, `typescript-engineering-v1`, `csharp-engineering-v1`, `c-engineering-v1`, `cpp-engineering-v1`, `go-engineering-v1`, `rust-engineering-v1`, `html-engineering-v1`, `sql-engineering-v1`, курс алгоритмов использует профиль JavaScript

В SQL уроки с 1 по 48 рассчитаны на SQLite, уроки с 49 по 60 на PostgreSQL и профиль `sql-postgresql-engineering-v1`, профиль нельзя выбирать только по `language:sql`, сервер сверяет точный идентификатор из сохранённого задания, для PostgreSQL нужны отдельная временная база и условия проверки конкурентных транзакций

Сервер создаёт попытку, сохраняет файлы и версии, ставит её в очередь проверки, запускает доступные проверки в изолированной среде и передаёт код вместе с документом на ревью по критериям, критерии оценки и настройки сборки выбираются сервером, клиент не может прислать себе упрощённые правила

Для `review` значение `publicExamples[].expectedOutput` описывает результат работы, оно не является эталонным stdout, совпадение строк не означает зачёт, итог `accepted` разрешён только после выполненных критериев, при замечаниях возвращай `wrong_answer` с понятным объяснением в `feedback.summary`, замечания к файлам в `feedback.diagnostics`, результаты критериев в `feedback.tests`

Проверяющий процесс должен уметь работать с несколькими файлами и учитывать требования конкретного профиля, некоторые примеры в теории показывают отдельный фрагмент, ученик собирает законченное решение по условию, учебные фрагменты не являются готовыми серверными тестами

Ревью может занять больше 30 секунд, это текущий предел одного ожидания фронтенда, после него попытка остаётся на сервере, результат можно открыть через историю урока, статусы контракта остаются `queued`, `running`, `finished`, для ручного ревью оставляй попытку в очереди до обработки, новую несовместимую строку статуса фронтенду передавать не нужно

В пакете описаны требования и критерии, исполняющие среды, закрытые тесты и система работы проверяющих реализуются в бэкенде, пока эта часть не подключена, текущий локальный режим продолжает показывать сообщение о разработке

## Как отправляется решение урока

После включения HTTP режима редактор сохраняет текущий черновик, формирует снимок файлов и отправляет его следующим запросом, оболочка `data` в запросе не используется

```http
POST /api/v1/submissions
Content-Type: application/json
Accept: application/json
Idempotency-Key: 79304f76-ef6e-4e45-a871-891390a2e28f
```

```json
{
  "lessonId": "python-01",
  "lessonVersion": 1,
  "exerciseId": "python-01-practice",
  "exerciseVersion": 1,
  "language": "python",
  "runtimeProfileId": "python-intro-v1",
  "files": [{"path": "main.py", "code": "print(\"Привет\")\n"}],
  "stdin": ""
}
```

Пример показывает формат, а не правильное решение конкретного урока, пользователь не передаёт свой идентификатор, сервер определяет его по авторизованной сессии

Сервер проверяет существование урока и практики, совпадение версий, доступ пользователя, язык, профиль исполнения, точные разрешённые пути файлов и размер в байтах, произвольные пути вне рабочей папки или другой профиль нельзя принимать только потому что их прислал клиент

Сервер сохраняет снимок файлов и ввода, создаёт попытку в базе и задачу в очереди, отвечает HTTP статусом 202, соединение не нужно держать открытым до завершения компиляции или исполнения

```json
{
  "data": {
    "id": "submission_123",
    "lessonId": "python-01",
    "exerciseId": "python-01-practice",
    "lessonVersion": 1,
    "exerciseVersion": 1,
    "status": "queued",
    "verdict": null,
    "createdAt": "2026-09-14T12:00:00Z",
    "updatedAt": "2026-09-14T12:00:00Z",
    "isDemo": false,
    "feedback": null,
    "pollAfterMs": 800
  },
  "meta": {"schemaVersion": "1.0"}
}
```

Фронтенд затем вызывает `GET /api/v1/submissions/submission_123`, сервер возвращает текущее состояние той же попытки, после завершения в ответ добавляются исходные `files`, `stdin`, версии и `feedback`

## Что должен делать сервер проверки

Исполнение кода находится только на бэкенде, отдельный обработчик очереди получает попытку, выбирает закреплённую версию среды, создаёт изолированную рабочую папку, размещает разрешённые файлы, компилирует код если это требуется, запускает проверки и сохраняет результат

Код ученика нельзя запускать внутри основного процесса API, обработчику нужны изоляция от приложения и базы пользователей, лимиты CPU и памяти, ограничение времени, количества процессов и объёма вывода, сеть для учебного кода должна быть отключена

Скрытые тесты и ожидаемые ответы хранятся только на сервере, их нельзя класть в публичные файлы фронтенда или возвращать в `feedback`, пользователю можно показать подробности публичного примера и безопасное описание ошибки

Для `program` сервер запускает программу и проверяет её результат, для `query` создаёт учебную SQLite базу и проверяет запрос, для `document` проверяет структуру HTML и нужные свойства CSS в изолированной среде, пользовательский HTML не вставляется в DOM сайта

Точных исполняемых контейнеров, скрытых тестов и рабочего обработчика очереди в этом репозитории нет, файл профилей описывает требуемые возможности, реализация этих компонентов относится к бэкенду релиза

## Состояния попытки и обратная связь

При `queued` попытка ждёт очереди, при `running` сервер её обрабатывает, в обоих случаях `verdict` равен `null`

При `finished` поле `verdict` содержит `accepted`, `wrong_answer`, `compilation_error`, `runtime_error`, `time_limit`, `memory_limit` или `internal_error`, при техническом сбое сервиса можно вернуть `failed` с `internal_error`

Настоящие попытки имеют `isDemo:false`, прежний статус `not_evaluated` оставлен в схеме для совместимости со старыми образцами, текущий локальный режим таких попыток не создаёт и не показывает

Объект `feedback` может содержать `summary`, `stdout`, `stderr`, `diagnostics`, `tests`, диагностика содержит `file`, `line`, `column`, `message`, `severity`, номера строк и столбцов начинаются с единицы

Публичный результат теста содержит `name`, `passed`, необязательные `message`, `expectedOutput`, `actualOutput`, для секретного теста подробные входы и ответы не передаются

Для зачёта урока фронтенд проверяет `finished`, `accepted`, `isDemo:false` и совпадение идентификаторов и версий с открытой практикой, результат другой версии не засчитывается, отметка прочитанной теории хранится отдельно

Уроки пакета используют `completionPolicy:server_accepted_submission`, при принятом решении сервер должен сам сохранить прохождение в своей базе, изменение массива localStorage на клиенте не является серверным подтверждением

## История и повторная отправка

При открытии урока фронтенд вызывает `GET /api/v1/submissions?lessonId=python-01`, сервер возвращает последние 20 попыток текущего пользователя, новые первыми, пустая история имеет тело `{"data":[],"meta":{"schemaVersion":"1.0"}}`

Каждая запись истории должна содержать те же идентификаторы, статусы и версии, а также исходные файлы и ввод, при выборе записи фронтенд дополнительно запрашивает попытку по её идентификатору

Доступ к истории и отдельной попытке проверяется по пользователю на сервере, знание чужого идентификатора не должно давать доступ к чужому коду

Одинаковое тело повторной отправки использует тот же `Idempotency-Key`, сервер связывает ключ с пользователем и хешем запроса, одинаковый ключ с одинаковым телом возвращает существующую попытку, одинаковый ключ с другим телом возвращает ошибку 409

После изменения кода или ввода создаётся новый ключ, при потере ответа повтор не должен создавать второй запуск или повторно выдавать награду, ключ и попытку нужно сохранять надёжно до ответа API

Обычный запрос имеет таймаут 10 секунд, ожидание проверки ограничено 30 секундами на клиенте, это не означает отмену серверной задачи, в уроках есть повторный запрос статуса, в отдельных задачах повторная отправка неизменённого кода получает ту же попытку и возобновляет ожидание

Интервал опроса берётся из `pollAfterMs` или настройки 800 миллисекунд, клиент ограничивает его диапазоном от 300 до 5000 миллисекунд

## Отдельные задачи JavaScript

Их публичный реестр находится в `task-import.json`, идентификаторы `reverse`, `sum`, `palindrome`, `unique`, `fizzbuzz`, `binary`, исходное имя проверяемой функции берётся сервером из поля `fn` реестра

Для этих задач используется отдельный профиль `javascript-functions-v1`, сервер должен загрузить файл `solution.js`, найти функцию из реестра задачи и проверить возвращаемые значения на своих аргументах, это отличается от проверки консольного вывода обычного урока JavaScript

Запрос отправляется в `POST /api/v1/task-submissions`, используются те же заголовки и правило идемпотентности

```json
{
  "taskId": "reverse",
  "taskVersion": 1,
  "language": "javascript",
  "runtimeProfileId": "javascript-functions-v1",
  "files": [{"path": "solution.js", "code": "function reverseString(str) { return str; }"}],
  "stdin": ""
}
```

Сервер возвращает HTTP 202 и попытку с `taskId`, `taskVersion`, `id`, `status`, `verdict`, датами, `isDemo:false` и `feedback`, поля урока и его практики для этого запроса не используются

Следующие запросы идут в `GET /api/v1/task-submissions/{submissionId}`, сервер возвращает состояние той же попытки, финальный ответ проверяется на совпадение задачи и её версии, фронтенд только показывает результат и сохраняет локальную отметку после принятия сервером

Истории отдельных задач в интерфейсе пока нет, локальное начисление XP после решения удалено, сервер должен начислять опыт самостоятельно и отдавать актуальные показатели через будущий API профиля

## Ошибки и версии

Неуспешный HTTP статус сопровождается JSON объектом `error`, поле `message` показывается пользователю, HTML страница ошибки не подходит

```json
{
  "error": {
    "code": "CONTENT_VERSION_MISMATCH",
    "message": "Версия задания изменилась, обновите урок",
    "details": {"expectedLessonVersion": 2},
    "requestId": "request_123"
  }
}
```

Используй 401 для отсутствия авторизации, 403 для отсутствия доступа, 404 для отсутствующего материала или попытки, 409 для несовместимой версии или конфликта ключа, 413 для превышения размера, 422 для неправильного запроса, 429 для ограничения частоты, 503 для недоступной проверки

Для отсутствующего исполнителя пример API возвращает `RUNNER_NOT_CONFIGURED`, локальный адаптер отклоняет прямой вызов отправки с `PROJECT_IN_DEVELOPMENT`, форма в локальном режиме показывает сообщение ещё до обращения к адаптеру

Поле `schemaVersion` задаёт версию формата ответа, сейчас это строка `1.0`, поле `contentVersion` и версия курса являются строками версии комплекта, версии урока, упражнения и отдельной задачи являются положительными целыми числами

При несовместимом изменении условия, шаблона или тестов увеличивай соответствующую версию, старое решение не проверяется как новое без явного решения на сервере, несовместимый черновик урока фронтенд переносит в архив локальных черновиков и открывает новый шаблон

## Авторизация и CORS

Текущий `api.js` использует `credentials:same-origin`, при API на том же домене браузер передаст cookie этого домена, сервер должен проверять сессию и права на каждый защищённый запрос

Если в HTML присутствует meta элемент с именем `csrf-token`, адаптер добавляет его содержимое в заголовок `X-CSRF-Token` для изменяющего запроса, получение и обновление такого токена нужно связать с реальной авторизацией

При API на другом домене для cookie авторизации потребуется явно изменить транспорт на `credentials:include`, настроить конкретный разрешённый origin, разрешение credentials и cookie, автоматически такое переключение проект не делает

Bearer токен сейчас автоматически не добавляется, если выбрана такая схема, получение токена и заголовок `Authorization` нужно реализовать в адаптере и процессе входа, страница демонстрационного профиля не заменяет авторизацию

## Профиль и прогресс в полноценном релизе

Сейчас профиль, записанные курсы, прочитанные уроки, черновики, локальное отображение прохождения, избранное, настройки и история активности хранятся в localStorage под ключом `logickernel.v1`

Отдельные черновики лежат в `state.drafts`, черновики практик уроков в `state.lessonDrafts`, архив несовместимых версий в `state.lessonDraftArchive`, ключи отправки отдельных задач в `state.taskRequests`, отметки чтения в `state.lessonReads`, подтверждённое отображение уроков в `state.completed`, отметки отдельных задач в `state.solved`

Старый ключ `logickernel.submissions.v1` больше не читается и не изменяется приложением, в нём могут остаться прежние демопопытки пользователя, это не серверная история и в релиз импортировать её как доказательство прохождения нельзя

Для релиза нужны серверные данные пользователя, зачислений на курсы, прохождений, попыток, опыта, настроек и сертификатов, сервер должен быть источником истины, локальное хранилище можно оставить для черновиков и кеша

Один возможный контракт будущего аккаунта, эти методы пока не вызываются текущим фронтендом и не входят в реализованный адаптер

```http
GET /api/v1/me
GET /api/v1/me/progress
PATCH /api/v1/me
POST /api/v1/enrollments
POST /api/v1/lesson-reads
GET /api/v1/certificates
```

При реализации нужно добавить методы в `api.js`, загрузку профиля и прогресса в инициализацию `app.js`, заменить изменения локального профиля и записи на курсы серверными запросами, после принятой попытки обновлять прогресс из ответа сервера или отдельного метода

Зачёт, XP, достижения и сертификаты вычисляются на сервере после подтверждённой проверки, начисление должно быть идемпотентным, изменение пользовательского JavaScript или localStorage не должно давать награду на сервере

Чтение можно хранить отдельно от решения, для сертификата сервер проверяет политику завершения курса, пользовательское скачивание текущего SVG сертификата не является настоящей выдачей документа

## Как проверить подключение до релиза

Пример API материалов запускается из корня проекта следующей командой

```sh
node backend-package/serve.mjs
```

Чтобы посмотреть фронтенд с этим API, временно поставь `mode:http` и `baseUrl:http://127.0.0.1:4180/api/v1` в конфигурации как строковые значения, запусти `start.cmd` и открой сайт через HTTP

Пример API разрешает обращения локального HTTP фронтенда, отдаёт готовые материалы и ошибку на отправку решений, он не является сервером авторизации или проверки кода

Для реального подключения вместо примера нужен твой сервер по описанному контракту, в Network должны появиться GET запросы материалов и POST запросы решений, локальный файл `mock-bundle.js` в режиме HTTP не загружается

## Сборка и проверки

Команды выполняются из корня проекта, перед браузерной проверкой останови обычный сервер на порту 4173, проверке также нужен свободный порт 9337

```sh
node tools/build-content.mjs
node backend-package/validate.mjs
node tools/verify-contract.mjs
node verify.mjs
powershell -File tools/package-backend.ps1
```

Для повторной сборки архива достаточно последней команды, она сама пересобирает материалы и проверяет пакет, после изменения документации архив тоже нужно обновить

Автоматические проверки подтверждают структуру данных и поведение интерфейса, предметная редактура курсов, серверные тесты по языкам, реализация авторизации и нагрузочная проверка серверных сред относятся к подготовке полноценного публичного релиза
